## `AACAgent`: the pipeline (`src/agent/agent.py`)

`AACAgent` is a stateful class, one instance per session/process, that on each call to `run(raw_input)` executes 6 phases in sequence:

1. **Decision**: a fast, separate LLM call decides whether time/schedule context is needed to understand the input (`needs_context: bool`), via `prompts.build_decision_prompt`.
2. **Context**: if needed, calls the `get_time` / `get_schedule` MCP tools and formats a compact text block to inject into the prompt, in `context.py`.
3. **Planning**: the planner LLM (a larger system prompt, with few-shot examples) generates 5-10 natural-language concepts from the input + history + context, via `prompts.build_planner_prompt`.
4. **Retrieval**: each concept is resolved into one or more ARASAAC keywords (`resolve.py`) and used to query `search_pictograms` (`mcp_server/tools/arasaac.py`).
5. **Synset expansion**: the candidate pool is enriched by searching for pictograms linked to the same WordNet synsets, semantic synonyms, via `search_pictograms_by_synset`.
6. **Ranking** + window fill: candidates are ordered with a deterministic strategy, not another LLM call, and trimmed to the final window (`max_results`), in `ranking.py`.

At the end, the turn is saved in `SessionMemory`, conversation history + shown/selected pictograms, used by subsequent turns to build the history injected into the prompt.

### Why "two-phase"

The class also supports a legacy mode (`use_two_phase=False`): a single LLM call that decided, contextually, whether to call the tools and which concepts to generate. It was replaced by the two-phase flow, separate decision + planning, because the "is context needed?" decision is a simpler problem and can use a much shorter prompt, saving tokens/latency, and the planner, when invoked, already has the context available and doesn't need to guess whether to call it.

Legacy mode is kept only for compatibility with old scripts.

### Diagnostic fields

`AACAgent` exposes several `last_*` attributes (e.g. `last_plan_method`, `last_resolve_info`, `last_synset_added`, `last_pool_ids`, `last_context_block`) populated on each `run()`. They serve two purposes:

1. debugging/logging, each phase writes an informational log line to `logs/agent.log` (see § Data on disk)
2. evaluation, the scripts in `eval/` read these fields to compute metrics without having to re-parse the logs.

### `EvalContext`

The `EvalContext` dataclass, at the top of `agent.py`, allows injecting fake responses for `get_time`/`get_schedule` and forcing `needs_context`, bypassing both the real MCP calls and the LLM decision phase. Used exclusively by the evaluation notebooks in `eval/`, which simulate multi-turn conversations with teacher forcing: at each turn they inject `gold_id` as if it were the real user's choice.

## Interchangeable LLM backends (`src/agent/backends.py`)

The agent doesn't depend on a specific inference engine, it depends on the abstract `LLMBackend` interface (`chat(system, user) -> str` + a `model_id` property). Three concrete implementations:

1. `OllamaBackend`: logical default if nothing else is specified. Talks to the Ollama HTTP daemon (`localhost:11434`), requires `ollama pull <model>`.
2. `LlamaCppBackend`: the actual production backend (`agent_use_llamacpp: true` in `user_settings.json`). Loads the `.gguf` file in-process via `llama-cpp-python`, no external daemon. Lazy loading, only on the first `chat()`, with `unload()` to free RAM when switching models.
3. `HuggingFaceBackend`: GPU-cluster evaluation only (`eval/`). Uses `transformers`, supports INT8 quantization, not meant for local CPU use.

`src/api/server.py` picks `LlamaCppBackend` by default (see `_get_agent()`), mapping the model selected in the interface to the corresponding `.gguf` file via `settings.gguf_models`. If the file doesn't exist, it falls back to Ollama with a warning in the logs.

The `unload()` method avoids keeping two models in RAM at once during a model switch or a multi-model evaluation loop.

> Note: Ollama was used initially for consistency with the course labs, then Hugging Face for speed testing, and finally, per the tutor's suggestion, llama.cpp was chosen for more objective benchmarking. Even though llama.cpp is the only backend actually used now, all three were kept in the code since the implementation was already done.

## Prompts and parsing (`src/agent/prompts.py`)

Three distinct system prompts, all designed to return only JSON, no markdown or explanation:

- **Decision prompt** (`_DECISION_SYSTEM_PROMPT`): minimal, 2 few-shot examples, output `{"needs_context": bool}`.
- Planner prompt, full version (`_PLANNER_SYSTEM_PROMPT_FULL`, ~650 tokens): 7 examples, higher quality, slower inference.
- **Planner prompt**, short version (`_PLANNER_SYSTEM_PROMPT_SHORT`, ~330 tokens): 5 examples, used by default (`build_planner_prompt(full=False)`).

`build_planner_message()` builds the user message by concatenating session history (if present), context block (if present), and caregiver input.

On the first turn, empty history, an explicit hint is added instructing the planner to always start the concept list with `"I"`: the AAC user always refers to themselves in the first person, regardless of how the caregiver describes them, "he", "she", "you"...

> Note: both the full and short planner prompts exist in the code, but only the short version is actually used. The full version was meant as an extra flag for combinatorial evaluation, full vs. short prompt as one more axis to test, but there were already too many variables in play, and after trying it a few times I didn't notice any clear advantage, so I don't use it. I kept it in the code anyway.

### Robust 2-3 pass parsing

Each parser follows the same progressive-pass pattern:

1. Standard JSON extraction, strips any markdown fences, looks for a balanced `{...}`.
2. Regex salvage on individual fields, for malformed but recoverable JSON.
3. Handles the case of JSON truncated by `max_tokens`, a concept list without a closing `]`, deduplicating any token repeated in a loop.

This approach exists because the small models (3B) used in production occasionally truncate output or repeat a token, the system degrades gracefully instead of failing the whole turn.

## Concept → keyword resolution (`src/agent/resolve.py`)

Every concept generated by the planner (e.g. `"go out"`, `"headphone"`) must be translated into an exact keyword from the ARASAAC catalog before it can be searched, the ARASAAC API does literal, not semantic, matching. `resolve_concept()` tries, in order, 5 strategies and stops at the first one that produces a match:

| # | Strategy      | What it does                                                                                                 | Example                                             |
| - | ------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| 1 | `exact`     | Lowercases the concept, case-insensitive lookup in the ARASAAC keyword set (`_kw_set`), no transformation  | `"Banana"` → `"banana"`                        |
| 2 | `lemma`     | spaCy lemma (base/dictionary form) of the whole phrase, catches plurals, conjugations                        | `"cookies"` → `"cookie"`                       |
| 3 | `hyphen`    | Normalizes spaces ↔ hyphens, looks up both variants, catches hyphenated ARASAAC compounds                   | `"go out"` → `"go-out"`                        |
| 4 | `lemma_alt` | Same as step 2, but on the hyphen-normalized form from step 3                                                | `"going out"` → `"going-out"` → `"go-out"`  |
| 5 | `token`     | Splits into tokens, lemmatizes each separately, matches on any single token                                  | `"loud headphone"` → `"headphone"`             |
| 6 | `embedding` | Sentence-embedding nearest-neighbour search over precomputed catalog embeddings, last resort, semantic match | `"earmuffs"` → nearest neighbour `"headphone"` |

If none of the first steps find anything, the whole pipeline is retried after stripping leading/trailing articles/determiners (`_strip_determiners`, e.g. `"a banana"` → `"banana"`).

Every call also returns a method label (`exact`/`lemma`/`hyphen`/`lemma_alt`/`token`/`embedding`/`none`), used in logs and evaluation metrics to see how often the agent relies on each step.

### Embedding fallback

`_EmbeddingIndex` is a lazy per-language singleton that loads `datasets/{lang}/keyword_embeddings.npz`, already present for `en`, generated by `datasets/build_keyword_embeddings.py`, must be regenerated manually for other languages. If the file is missing for a language, this step is simply a no-op, it's not a requirement for the agent's basic operation, just an optional recall improvement when the first steps fail. The embedding model (`all-MiniLM-L6-v2` via `sentence-transformers`) is only loaded on the first actual call to `nearest()`.

## Ranking and final window (`src/agent/ranking.py`)

After retrieval, the candidates, potentially hundreds, are ordered and trimmed to `max_results`, default 25, in `user_settings.json`. Two strategies are available in `STRATEGIES`, selectable via `ranking_strategy` when instantiating the agent:

`sequential_blocks`, default/baseline: candidates are grouped one block per concept, in the same order the planner generated the concepts, internally sorted by quality (`aac_color` > `aac` > non-violent > non-sexual). Simple and predictable, but if the first concept alone already fills, or nearly fills, `max_results`, later concepts can end up pushed off the visible window entirely. Used as the baseline in evaluations because it's the simplest strategy, not because it's the best one.

Example: 3 concepts `["I", "want", "go out"]` → window `[I-1, I-2, I-3, ..., want-1, want-2, ..., go_out-1, ...]`, `"I"` is exhausted before `"want"` even starts.

`round_robin_weighted`: instead of one full block at a time, it interleaves picks across the concept-groups, taking a bit from each in turn, rather than emptying one group before touching the next. The draw order is weighted, earlier concepts still get priority, but the weight decays exponentially with concept rank (`0.7^rank`). The "deficit round-robin" scheduling algorithm implements this fairly: each group accumulates a credit each round proportional to its weight and spends it to emit pictograms, so higher-weight groups get picked more often without ever fully starving lower-weight ones. This solves the `sequential_blocks` problem: concepts generated later still get a fair share of visible slots instead of disappearing behind a large first block.

Same 3 concepts, `round_robin_weighted` → window `[I-1, want-1, I-2, go_out-1, want-2, I-3, ...]`, all three concepts appear early, weighted toward `"I"` but without pushing `"go out"` off-screen.

Both strategies only exclude pictograms actually selected in recent turns, not those merely shown and ignored, so as not to over-restrict the search space when the window is already large.

## Session memory (`src/agent/session.py`)

`SessionMemory` accumulates a `Turn` for each call to `run()`, storing the raw caregiver input, the pictograms shown to the user that turn (`presented`), the pictogram(s) actually chosen (`pictograms`, starts as the full presented list and is narrowed down to a single item once the user calls `/select`), and the turn's time slot.

Each `Turn` tracks two different sets of pictogram IDs, but only one actually matters for ranking. `recently_selected_ids()`: IDs the user actually picked via `/select`, excluded by the ranking strategies from being shown again so the user isn't offered the same pictogram twice. `recently_presented_ids()`: all IDs shown on screen recently, whether picked or ignored, a diagnostic-only field (e.g. inspected in `eval/`) that does not feed into ranking, listed here just so it isn't confused with the one above.

`prompt_summary()` produces the textual history summary injected into the planner prompt, format: `Turn N (time_of_day): "input" → chosen_label`, this is what lets the planner remember the conversation so far.

This module also hosts the lazy singleton for the spaCy model (`_nlp()`, `en_core_web_sm` with the parser/NER disabled for speed), shared by `resolve.py` and the term-extraction fallback in `agent.py` (`_extract_terms`, used only when the planner LLM returns an empty list).

## Time/schedule context (`src/agent/context.py`)

`collect_context()` is the single entry point for obtaining `time_of_day` + schedule events, both in production, by actually calling the `get_time`/`get_schedule` MCP tools, and in evaluation, by reading mocks from `EvalContext`. `filter_schedule_by_time()` returns a single event, the one closest to the current time slot. `build_context_block()` formats everything into one compact line, e.g. `"time=afternoon (14:30) | schedule: Math class at 14:30:00 @ school"`, which is injected into the planner prompt: a flat, newline-free format, both for log readability and to avoid confusing the LLM.

## MCP server and tools (`src/mcp_server/`)

`server.py` instantiates a single `FastMCP("AAC Pictogram Service")` object shared by all tools, which register themselves with the `@mcp.tool()` decorator.

Worth being upfront that this isn't a "real" MCP setup in the sense most people mean when they talk about MCP. Normally a client and a server are two separate processes exchanging JSON-RPC messages over a protocol boundary (stdio, SSE, or HTTP), even on the same machine. Here that boundary isn't there at runtime: `AACAgent` just imports the tool functions (`search_pictograms`, `get_time`, etc.) and calls them as regular Python functions, same process, same memory space, no serialization or round-trip involved.

`../test/mcp_protocol_demo.ipynb` shows the alternative: the same tools, started as a real subprocess and called over an actual stdio JSON-RPC connection, roughly doubling per-call latency compared to the in-process calls used everywhere else.

So why are they written as MCP tools at all, if they're only ever called in-process? Two reasons. Going through the actual protocol here would only add serialization overhead with zero benefit, since "client" and "server" are the same process anyway, so it made more sense to skip the middleman. And decorating them with `@mcp.tool()`, typed Pydantic models, structured returns, costs almost nothing today but keeps the door open: the same functions could later be attached to a real `FastMCP` server and exposed over stdio/SSE without rewriting them, since the protocol compliance is already there.

### `tools/arasaac.py`

Four main tools, each following the same logic: try the local dataset first, fall back to the live ARASAAC API if the local one isn't available.

`list_keywords(lang)`: all catalog keywords for a language, used at agent startup to build the `_kw_set` used by `resolve.py`.

`search_pictograms(keyword, lang, max_results)`: literal keyword match → list of pictograms, not semantic search.

`search_pictograms_by_synset(synset_id, wordnet, lang)`: all pictograms linked to a WordNet synset, used by the synset expansion phase of the agent.

`get_pictogram_metadata(pictogram_id, lang)`: full metadata for a single pictogram by ID.

`_image_url()` decides whether to return a local proxy URL (`/api/images/{id}`, when `USE_LOCAL_DATASETS=True`) or the direct ARASAAC CDN URL, this is what makes the app usable offline once images have been downloaded.

### `tools/time_tool.py` and `tools/schedule_tool.py`

`get_time()`: returns the current datetime + slot (`morning`/`afternoon`/`evening`/`night`), computed from the thresholds in `config.DAY_TIME_THRESHOLDS`.

`get_schedule(date_str)`: the day's events from Google Calendar (OAuth2, requires `app/credentials/credentials.json` + an initial interactive login that generates `token.pickle`) or Apple iCloud via CalDAV (app-specific password in `app/.env`). The active provider is `calendar_provider` in `user_settings.json` (`"google"` or `"apple"`) — not `.env`, so switching provider means editing that JSON key (or using the Settings panel, which does the same via `PATCH /settings`), not touching environment variables. Only one provider is queried per call, there's no branch that merges both.

**Google setup**: create an OAuth2 client in [Google Cloud Console](https://console.cloud.google.com) (Calendar API enabled, credential type "Desktop app"), download the JSON, save it as `app/credentials/credentials.json`. The first `get_schedule()` call with `calendar_provider: "google"` opens a browser for an interactive login, then writes `app/credentials/token.pickle`, silently refreshed after that. `GOOGLE_CALENDAR_ID` in `.env` defaults to `"primary"`.

**Apple setup**: generate an app-specific password at [appleid.apple.com](https://appleid.apple.com) → Sign-In and Security → App-Specific Passwords (this is not your regular Apple ID password). Set `APPLE_USERNAME` and `APPLE_APP_PASSWORD` in `app/.env` (see `.env.example`).

### `dataset_cache.py`

A singleton (`_DatasetCache`) that loads into memory, on first request and only once per process, the per-language JSON files under `app/datasets/{lang}/` (see [`datasets/README.md`](datasets/README.md) for the file format). All `load_*` methods return `None` instead of raising exceptions on missing files, so the tools can transparently fall back to the live API. `invalidate()` forces a reload from disk, called automatically after a dataset update via `/datasets/update`.

## Configuration: `config.py` vs `settings.py`

A clear distinction, also stated in `settings.py`'s docstring.

`settings.py`: values modifiable by the user, read/written by the Settings panel of the interface (via `GET`/`PATCH /settings`). Persisted in `app/user_settings.json`, gitignored, created automatically on first run with the defaults defined in `_DEFAULTS`. Examples: active LLM model, results window size, number of memory turns, calendar provider.

`config.py`: application constants that are not user-settable, e.g. ARASAAC base URL, time-of-day thresholds, macro-category map, plus sensitive credentials loaded from `app/.env` via `python-dotenv`, never exposed via the API. It imports the user-facing values from `settings.py` to re-export them under simple names (`AGENT_MAX_RESULTS`, `LANG`, etc.) used throughout the rest of the code.

The `app/.env` file should be created by copying `app/.env.example` and filling in the credentials needed only if that feature is actually used (Apple/Google Calendar, HuggingFace for cluster evaluation). None of these are required for basic operation, pictograms + local LLM.

## HTTP API (`src/api/server.py`)

A stateful FastAPI server: a single `AACAgent` instance shared at the process level (`_get_agent()`), designed for a single user/local device at a time, not for multi-tenancy.

### Endpoints

`POST /run` runs a full turn, caregiver text in, a grid of candidate pictograms out. `POST /select` records the user's choice for the current turn and updates session memory. `POST /reset` resets the session and history. `GET /session` returns the full session history, for the sidebar.

`GET`/`PATCH /settings` reads and updates `user_settings.json`. `GET /health` reports model status, Ollama reachability, and whether a warmup is in progress.

`GET /images/{id}` proxies pictogram PNGs from the local dataset or the CDN. `GET /categories` and `GET /by_category` expose the macro-category tree used by `Browse`.

`GET /datasets/status` reports the status of local datasets per language. `POST /datasets/update` starts a dataset update, streaming logs back as Server-Sent Events.

### Background model warmup

Loading a `.gguf` model into RAM and running its very first inference is slow, multiple seconds, because llama.cpp has to build the system-prompt KV-cache from scratch. To avoid making the user's first real message pay that cost, the server pre-warms the model in the background at two moments: at boot (FastAPI `lifespan` hook) and on every model change (`PATCH /settings` with a different `agent_default_model`).

In both cases the `.gguf` file loads on a separate background thread, non-blocking, then a dry inference call with the real planner system prompt but throwaway input forces llama.cpp to build and cache the KV-cache immediately, so the expensive prefill has already happened by the time a real message arrives.

`GET /health` exposes `warming_up` and `warmup_error`, and the frontend polls it to show a "loading model" banner instead of letting the first real `/run` sit there for many seconds looking frozen.

### Why `asyncio.to_thread()` in `/run`

`agent.run()` is a blocking, CPU-bound call, it can take 10-60s with a 3B model on CPU. Running it directly in an async endpoint would block uvicorn's entire event loop, causing "socket hang up" errors on the Vite proxy side before the response even arrives. `asyncio.to_thread()` moves it to a thread pool, leaving the event loop free to respond to keep-alives in the meantime.

## Frontend (`frontend/`)

React 18 + Vite 5, no external state-management framework, only native React hooks. The Vite proxy (`vite.config.js`) forwards all `/api/*` calls to the backend on `:8000`, rewriting the prefix, this is what makes the app accessible both from `localhost` and from other devices on the LAN, e.g. a tablet, thanks to `host: true` in the Vite server config.

```
frontend/src/
  App.jsx                    # root component: application state, warmup/health polling
  hooks/
    useAgent.js                 # /run, /select, /reset, /session, /health
    useSettings.js                # /settings (GET/PATCH)
    useDatasets.js                  # /datasets/status, /datasets/update (manual SSE parsing)
  components/
    InputBar.jsx                # caregiver text input
    PictogramGrid.jsx / PictogramCard.jsx   # results grid, tap-to-select
    SessionSidebar.jsx          # history of the current session's turns
    SettingsPanel.jsx           # settings panel
    DatasetPanel.jsx            # datasets panel (update progress via SSE)
    CategoryBrowser.jsx         # two-level macro-category navigation ("Browse" button)
```

Main flow in `App.jsx`: the user types and submits (`/run`) → receives a grid → taps a pictogram (`handleSelect`) → this calls `/select` and then automatically re-runs `/run` with the same text, because the updated session memory changes what the planner will suggest as the next concept, designed to build a sentence concept-by-concept, not as a single isolated turn.

## Data on disk: `datasets/`, `models/`, `logs/`, `credentials/`

`datasets/` has its own detailed [`README.md`](datasets/README.md), JSON file layout, `_meta.json` format, `update_datasets.py` commands, not duplicated here.

`models/` contains the `.gguf` files referenced by `gguf_models` in `settings.py`, one per Ollama alias: `qwen2.5:3b`, `llama3.2:3b`, `granite4:3b-h`, `mistral:7b`. Gitignored folder due to size, and not included in the submission zip either, see [root README](../README.md#missing-data-this-is-a-stripped-down-archive) to download one, or use the Ollama backend instead.

Download the exact files `gguf_models` expects, all from the same quantizer so filenames match with no renaming needed:

```bash
hf download bartowski/Qwen2.5-3B-Instruct-GGUF Qwen2.5-3B-Instruct-Q4_K_M.gguf --local-dir models

# hf download bartowski/Llama-3.2-3B-Instruct-GGUF Llama-3.2-3B-Instruct-Q4_K_M.gguf --local-dir models

# hf download bartowski/ibm-granite_granite-4.1-3b-GGUF ibm-granite_granite-4.1-3b-Q4_K_M.gguf --local-dir models

# hf download bartowski/Mistral-7B-Instruct-v0.3-GGUF Mistral-7B-Instruct-v0.3-Q4_K_M.gguf --local-dir models
```

Total for all four: ~10 GB.

`logs/`: centralized configuration in `logging_config.py`, called by `api/server.py` at startup, which produces 4 distinct files. `app.log`: everything, DEBUG+, rotation 2 MB × 5. `errors.log`: WARNING+ only, rotation 1 MB × 3. `agent.log`: a readable, phase-by-phase trace of each turn (`[INPUT]`, `[DECIDE]`, `[CTX]`, `[PLAN]`, `[RESOLVE]`, `[SYNSET]`, `[RANK]`, `[RESULT]`), the most useful file for understanding what the agent did on a specific turn. `prompt.log`: verbatim prompts, system+user, sent to the LLM on each call, to inspect exactly what the model sees. `clear_logs.sh`: utility script to clear the logs.

`credentials/`: local secrets for the calendar integration (`credentials.json`/`token.pickle` for Google OAuth2). Never committed, see `.gitignore`, only needed if using `calendar_provider: "google"`.
